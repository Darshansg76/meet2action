# Meet2Action

Meet2Action extracts agreed action items from short English meeting notes. The shared engine returns tasks, owners, original deadline phrases, supported calendar dates, exact source quotes and missing-detail warnings. A Streamlit app and an A/B/C evaluator use the same public extraction function.

This checkout currently contains the prompts, dataset allocation, annotation checker and Darshan's offline evaluation tooling. `service.py` and `app.py` have not been supplied. Live extraction, application integration and benchmark measurements are pending those handoffs.

## Shared extraction contract

Both the app and evaluator import this function from `service.py`:

```python
def extract_actions(notes, meeting_date=None, method="B"):
    ...
```

Inputs are non-empty raw notes with at most 25 non-empty lines and 6,000 characters, an optional ISO meeting date and method A, B or C. Dataset snippets have a minimum of three non-empty lines. Non-empty source lines are numbered L01, L02, etc. Keep at most eight actions. A uses instructions; B adds fixed examples; C independently starts with B's prompt and permits at most one repair. A and B use one logical model call each; C uses at most two. Transport retries are separate from logical call counts.

The return value is a plain JSON-compatible dictionary. This contract example is illustrative; its timing and model ID are placeholders, not measurements:

```json
{
  "status": "ok",
  "actions": [{
    "task": "Send the slides",
    "owner": "Maya",
    "deadline_text": "tomorrow",
    "due_date": "2026-11-12",
    "evidence": [{"line_id": "L01", "quote": "Maya: I will send the slides tomorrow."}],
    "warnings": []
  }],
  "message": "",
  "meta": {
    "latency_ms": 0,
    "model_calls": 1,
    "input_tokens": null,
    "output_tokens": null,
    "model": "configured_model_id",
    "raw_responses": [],
    "validation_errors": []
  }
}
```

Keep every response and metadata key present for all statuses. `ok` includes valid empty results. `review_required` and `api_error` return no accepted actions and an explanatory message. Downloads require `ok`. The engine retains raw model response strings and reports actual model, call count, elapsed time and available token usage, including repair usage. Unavailable token counts stay `null`.

The model's intermediate actions use `ambiguities`; final actions and dataset gold labels use `due_date` and `warnings`. Follow [ANNOTATION_GUIDE.md](ANNOTATION_GUIDE.md) for action policy, evidence, supported dates and warning order. `prompts.json` is the prompt authority.

## Inspect and run evaluation

This command works now. It checks two labelled development records without importing the engine, writing results or using an API:

```powershell
py -3 evaluate.py run --split development --ids M048 M049 --dry-run
```

A live run requires the engine, its dependencies and credentials. A full split also requires every selected record to be labelled; unfinished records are rejected rather than silently skipped. `--ids` explicitly selects a subset for a smoke check.

After the engine handoff, replace `ACTUAL_MODEL_ID` with the ID the engine reports in `meta.model`. Configure any generation settings in the engine first. `--setting NAME=VALUE` records those settings for reproducibility; it does not apply them to the provider. Supported setting names are `temperature`, `top_p`, `seed` and `max_output_tokens`. Confirm and record every setting used in the comparison.

```powershell
py -3 evaluate.py run --split development --ids M048 M049 --model ACTUAL_MODEL_ID --output-dir results/runs/smoke
py -3 evaluate.py run --split development --model ACTUAL_MODEL_ID --output-dir results/runs/development-final
```

Run the ten development cases with the engine and prompt owners, settle prompt changes, then freeze the final configuration. The held-out run follows only after all 40 test labels and the required independent reviews are ready:

```powershell
py -3 evaluate.py run --split test --model ACTUAL_MODEL_ID --output-dir results/runs/test-final
```

Each selected meeting runs A, B and C independently. There is no reuse of B's output for C. Forty test cases require 120 initial calls and up to 40 repairs; ten development cases add 30 initial calls and up to ten repairs. These estimates exclude transport retries and setup requests.

The run directory stores frozen dataset and prompt snapshots, a manifest with SHA-256 fingerprints of the dataset, prompts, service and evaluator, the expected model, declared settings, selection and Python version. `predictions.jsonl` is flushed to disk after every outcome, including failures, with the raw engine result, status, validation errors, wall time, token usage and model-call count. A wrong reported model stops the run after saving that failure.

To continue an interrupted run, repeat its exact command with `--resume`. Saved outcomes, including failures, are skipped. Resume requires unchanged inputs, evaluator, model, settings and selection. It can recover an incomplete final JSONL append. Earlier corruption is rejected. For a retry of a completed failed case or changed inputs, use a new run directory.

Run directories are intended for one evaluator process at a time. An unexpected engine exception is saved as `evaluation_error`; it is never converted into a successful empty result. The evaluator has no additional model-call retries.

## Review task matches and calculate scores

Prepare reviews only after every outcome in that run has been saved:

```powershell
py -3 evaluate.py review-template --run-dir results/runs/test-final --output results/runs/test-final/reviews.json
```

The template contains source gold and accepted predicted actions for reference. Read the original meeting in `dataset.json` and raw output in `predictions.jsonl` when judging evidence and omissions. For each meeting/method, enter a reviewer name, semantically match tasks one-to-one, judge owner and date correctness, mark unsupported predictions, and then set `complete` to `true`. Indices are zero-based. For example, a reviewed match looks like:

```json
{
  "gold_index": 0,
  "prediction_index": 1,
  "owner_correct": true,
  "date_correct": false
}
```

`owner_correct` includes correct `null` ownership. `date_correct` means both the original deadline phrase and normalized `due_date` are correct, including correct null values. `unsupported_prediction_indices` lists unmatched predictions with no supporting agreed action. A duplicate of a real action is a false positive, but does not automatically count as an unsupported action. Unmatched gold actions are false negatives. Failed outcomes also need a completed review and have no accepted predictions. Do not edit the reference actions to change a score; scoring uses frozen source records and saved predictions.

```powershell
py -3 evaluate.py score --run-dir results/runs/test-final --reviews results/runs/test-final/reviews.json --output results/runs/test-final/summary.json --table results/runs/test-final/comparison.md
```

Scoring requires exactly one completed review per outcome and rejects duplicate matches or indices outside the action lists. Reviews are tied to the exact manifest and prediction file by hashes. Reports include counts, failure statuses and these metrics:

| Metric | Definition |
| --- | --- |
| Task precision / recall / F1 | Micro-averages from human one-to-one matches; failed cases remain in gold totals |
| Owner / date correctness | Correct human judgments divided by matched tasks |
| Source-check pass rate | Accepted predicted actions whose complete evidence lines match exactly and include their stated owner and deadline |
| Valid-output rate | Outcomes with `ok` status and the agreed response shape / all attempted outcomes; source correctness is reported separately |
| No-action correctness | Valid empty outputs / gold meetings with no actions |
| Unsupported-action rate | Human-marked unsupported predictions / accepted predicted actions |
| Median latency | Evaluator wall time across every saved outcome, including failures |
| Calls and tokens | Totals only when every outcome reports them; known sums and coverage are also saved |

The JSON report uses `null` for undefined metrics or unavailable totals; the Markdown tables display `n/a`. Raw outputs with a non-ok status or invalid contract stay saved for inspection but supply no accepted predictions. Automated source checks cannot establish semantic task correctness, ownership or deadline meaning; those judgments require the team review.
